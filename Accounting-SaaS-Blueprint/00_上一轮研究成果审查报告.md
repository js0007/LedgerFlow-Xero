## 二、上一轮 MVP 设计全面审查（对照需求 §3.2）

### 2.1 架构与技术栈冲突（关键决策偏差）
1. **后端数据库与语言栈完全错位：**
   - `Accounting-SaaS-Blueprint/05_系统技术架构.md` 推荐的是 **TypeScript (NestJS/Fastify) 或 FastAPI + PostgreSQL 16**，且 `schemas/accounting_core.sql` 强依赖 PostgreSQL 特有语法（`UUID`、`gen_random_uuid()`、`TIMESTAMPTZ`、`JSONB`、`PL/pgSQL FUNCTION`、Row-Level Security 假设）。
   - **用户当前明确要求独立复刻技术栈为：Python + Flask API + SQLite + 高保真前端。**
   - **影响评估：** 若继续沿用 `accounting_core.sql` 无法直接在 SQLite 运行；必须重编一版严格兼容 **SQLite 3** 的核心 DDL（例如：用 `TEXT` 存 UUID 与 ISO-8601 日期时间；用 **精确最小货币单位整数 `INTEGER`（如分 cents 或 0.0001 缩放整型 `NUMERIC_SCALED`）** 替代无原生定点数算术校验的浮点风险，配合 Python `Decimal` 做计算、格式化为十进制字符串返回 API；用 SQLite 原生 `BEFORE UPDATE` / `BEFORE DELETE` `RAISE(ABORT, ...)` 触发器维持总账不可变性；在 Flask 服务层强制执行基于 `org_id` 的租户隔离与角色权限校验）。
