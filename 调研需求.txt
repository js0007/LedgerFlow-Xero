# Xero 产品深度研究与独立会计 SaaS 复刻设计

## 一、任务背景与总体目标

你现在担任本项目的首席产品研究员、资深会计系统架构师、前端架构师及 AI Coding 技术负责人。

我计划参考成熟的 Xero 会计 SaaS 产品，独立设计和开发一套面向澳洲中小企业及会计事务所的会计系统。

本次任务不是简单的 Xero 功能介绍，也不是立即开始编写业务代码，而是利用 AI Agent 的自主研究能力、Chrome DevTools、官方网站及公开 API，系统研究 Xero 的真实产品。

最终需要实现两个目标：

**目标 A：建立 Xero Research 产品研究资产库。**

让我能够系统理解 Xero 的产品设计、界面布局、核心交互、业务流程、数据对象、会计规则和技术实现思路。

**目标 B：形成 Accounting SaaS Blueprint 独立产品设计资产库。**

在研究事实的基础上，设计一套可供 Codex 等 AI Coding Agent 直接实施的产品规格，包括前端、API、数据库、会计引擎、业务状态、测试场景和实施路线图。

研究的最终价值不仅是产出文档，更是积累一套有证据、有业务依据、可追溯、可持续迭代、可驱动 AI 开发的工程资产。

# 三、核心研究原则

## 3.1 以真实产品为第一研究对象

不能只通过官方 API 文档或者网上文章推测产品功能。

必须实际探索 Xero Web 产品，理解：

- 功能入口在哪里
- 用户如何完成业务
- 页面如何组织
- 操作如何反馈
- 数据如何流转
- 不同模块之间如何关联
- 业务状态如何转换
- 哪些操作会影响会计账务

官方文档负责补充和验证真实观察。

## 3.2 以业务场景驱动研究

不要机械遍历页面后生成大量菜单说明。

研究应同时覆盖：

**产品结构维度**

理解 Xero 有哪些模块，以及模块之间的关系。

**业务链路维度**

理解一个业务如何从开始走到结束。

例如：

销售发票 → 审批 → 应收账款 → 收款 → 核销 → 总账 → 财务报表。

**会计核算维度**

理解每一步业务操作对会计分录、科目余额、税务和报表产生什么影响。

## 3.3 区分事实、官方规则与设计推断

所有重要结论必须明确证据来源。

采用以下分类：

- **Observed：** 实际在 Xero 中观察到的行为。
- **Documented：** Xero 或权威机构官方文档明确说明的规则。
- **Inferred：** 根据观察和专业知识形成的合理推断。
- **Proposed：** 我们为独立产品提出的设计方案。
- **Unknown：** 尚未确认，不能得出结论。

不得把 Inferred 或 Proposed 写成 Xero 的真实内部实现。

对于无法确认的内容，明确说明未知及验证方法。

## 3.4 优先理解原理，而不是复制表象

研究不能停留在：

“这个页面有哪些按钮、哪些字段”。

还需要理解：

- 为什么采用这种交互模式
- 页面解决什么业务问题
- 为什么存在这些状态
- 哪些规则属于会计原则
- 哪些规则属于 Xero 的具体产品选择
- 哪些能力可以独立抽象成通用组件
- 哪些设计值得复用
- 哪些设计不适合我们的 MVP

重点理解成熟产品背后的设计思想。

## 3.5 研究与独立产品设计分离

Xero Research 负责记录参考产品事实。

Accounting SaaS Blueprint 负责设计自己的系统。

两者必须能够互相追溯，但不允许混为一谈。

我们最终开发的是独立产品，不是直接依赖 Xero 运行的前端壳，也不是使用 Xero 数据库的接口代理。

## 3.6 控制研究深度与产出规模

不要为了展示工作量而生成大量重复文档。

采用逐步深入的研究策略。

先建立产品全景，再识别关键业务链路，然后深入研究必要模块。

不要对暂时不需要的功能进行无边界探索。

采用 P0、P1、P2 三层优先级。

## P0：必须深入理解和设计

这些是独立会计 SaaS 的核心。

1. 产品整体信息架构与全局导航
2. Dashboard 首页
3. Organisation / Tenant / 账套管理
4. Chart of Accounts 会计科目
5. Manual Journals 手工日记账
6. Journal / General Ledger 总账及分录
7. Trial Balance 试算平衡
8. Profit & Loss 损益表
9. Balance Sheet 资产负债表
10. Tax Rates / GST 税码与税务规则
11. BAS 基础计算
12. 会计期间与过账规则
13. 核心会计数据模型
14. 账务一致性及审计追溯

P0 不仅要研究页面，还要深入理解业务规则和数据模型。

## P1：研究业务流程和页面，第一阶段允许简化或占位

1. Contacts 客户及供应商
2. Invoices 销售发票
3. Bills 采购账单
4. Payments 收付款
5. Bank Accounts 银行账户
6. Bank Transactions 银行交易
7. Bank Reconciliation 银行对账
8. Cash Coding 银行流水分类
9. Tracking Categories 业务分析维度

P1 应理解：

- 页面结构
- 业务操作
- 核心字段
- 状态流转
- 数据关系
- 会计影响

但暂不要求实现完整的外部服务能力。

特别注意：即使发票、收款和银行界面暂时占位，其背后的基础记账规则仍需要在会计内核中得到验证。

## P2：浅度研究或暂不实现

1. Payroll
2. Inventory
3. Fixed Assets
4. Projects
5. Expenses 的高级能力
6. 第三方应用生态
7. 银行直连
8. ATO 直接申报
9. 完整邮件及通知服务
10. 复杂权限体系
11. 高级自动化规则

P2 只需要理解模块定位、依赖关系和未来扩展边界。

不要在本轮耗费大量时间深入研究。

## 6.3 Network 研究

针对关键业务操作观察：

- 请求路径
- HTTP Method

- 分页与筛选

## 7.5 财务报表

- GST 税码

- Accrual Basis

# 十、资产质量与可追溯要求

每项关键研究成果至少能够回答：

- 研究了什么
- 证据从哪里来
- 观察到了什么
- 官方文档如何解释
- 哪些是推断
- 对我们的产品有什么借鉴价值
- 对应哪个复刻设计
- 如何验证设计正确

建议为关键证据赋予稳定 ID，并在文档、规格和测试中建立引用关系。

例如：

页面证据 → 交互行为 → 业务规则 → 数据模型 → API 契约 → 测试案例。

如果一个关键设计结论缺乏证据，需要标记为待验证，而不是通过猜测补齐。

不得为了完善文档而编造 Xero 的真实行为。

# 十二、MVP 业务验收

以三笔业务作为第一阶段最小验收场景。

使用专用测试数据，金额单位为澳元。

### 场景一：销售发票

开具并批准一张含 GST 110 AUD 的销售发票。

预期分录：

借：应收账款 110

贷：销售收入 100

贷：GST 销项税 10

### 场景二：发票收款

客户支付 110 AUD，并核销第一笔发票。

预期分录：

借：银行存款 110

贷：应收账款 110

不得重复确认收入及 GST。

### 场景三：Cash Coding

另一笔 110 AUD 银行收入，直接分类为含 GST 的销售收入。

预期分录：

借：银行存款 110

贷：销售收入 100

贷：GST 销项税 10

### 最终结果

- 销售收入：200
- 银行余额增加：220
- 应收账款余额：0
- GST 负债：20
- BAS G1：200
- BAS 1A：20
- BAS 1B：0

以上为约定税码、会计政策及税务场景下的简化验收数据。

还必须验证：

- 借贷总额平衡
- 分录没有重复
- 账务能够追溯到原始单据
- 总账金额正确
- 试算平衡正确
- 损益表正确
- 资产负债表平衡
- GST 数据来源可以追溯

不能仅在报表页面写死上述结果。
